# Design

How the pipeline turns a short job spec into a finished action sequence, why each stage exists,
and what each quality gate catches. The numbers below come from measurements recorded while the
system was built; where a number came from one seed or one clip, the text says so.

## Goal

Produce short, character-consistent action sequences with as little hand work as possible,
while keeping the human in the two places a script cannot replace: picking the look, and
watching the result. Everything between those two points is meant to run unattended and to
fail loudly: every stage writes its state to disk, every gate is deterministic, and every
gate has a recorded positive control.

Three generation paths share one design:

| Path | Entry point | Renders on |
|---|---|---|
| Hosted, browser adapters | `make_video.js` | hosted video services via adapters (withheld) |
| Hosted, official API | `make_video_atlas.py` + `atlas_cloud.py` | an official REST API |
| Local GPU | `tools/h3_local.py`, `tools/h3_queue.py`, `tools/render_pass.py` | a local ComfyUI instance |

## The job spec

A job is one JSON file. See [`specs/example_duel_nox.json`](specs/example_duel_nox.json); ten more
examples sit beside it in `specs/`. A spec holds:

- **hero**: a key into `config/heroines.json`, plus a short appearance description;
- **fight_style**: a key into `config/fight_style_templates/` (clip-1 mode);
- **opponent**: either `mode: "prompt"` (described in text) or `mode: "ref"` (a recurring foe
  with a reference sheet, registered in `config/opponents.json`);
- **environment**: a short description in each prompt language;
- **escalation**: the clip-2 template (see below);
- **format, clips, clip_length, resolution**: geometry (e.g. 2 clips of 15 s at 720p);
- **palette**: a hero/enemy colour pair, chosen so the two always separate on screen.

`config/variety_pools.json` lists the heroes, styles, environments and palette pairs a planner may
combine, including per-style `heroes_allowed`, per-hero `styles_allowed` and `fixed_environment`
locks for modes that only make sense with one character or one setting.
`config/fight_styles.json` documents each mode; no code reads it.

Clip 1 (a **mode**) and clip 2 (an **escalation**) are chosen independently, so variety is
combinatorial rather than one fixed 30 s template. Shared escalations live in
`config/fight_style_templates/_escalations/`; the resolver checks the mode's own folder first.

`node make_video.js --spec <spec> --validate-only` renders every template for a spec and stops
before any generation stage, so a new mode can be checked for free.

## Generation chain

```
preflight -> sb1 -> clip1 -> sb2 (bridge) -> clip2 -> concat -> qa -> package -> manifest
```

**Storyboard first.** Each clip starts from a storyboard grid generated by an image model.
Video models follow a storyboard's action arc far better than a text-only prompt: they read the
board for camera, choreography and character, and the prompt mostly reinforces it. Grids are
sized to a ratio the image model can render exactly (3x3 cells of 16:9 = 16:9 overall; 3x4 =
4:3, see `tools/build_storyboard.py`); a ratio it cannot render gets re-framed, and the
composition the board exists to preserve is lost.

**Reference binding.** The clip prompt binds references by position: the hero sheet as
`@image1`, the storyboard as `@image2`, and an opponent sheet as `@image3` when the foe recurs.
The templates in `config/fight_style_templates/<mode>/` show the structure: an English storyboard
template (`sb_clip1_*_en.txt`) and a video template (`video_clip1_*_zh.txt`) with `{{SLOT}}`s
filled from the spec.

**The bridge.** One video call tops out at 15 s, so a 30 s sequence is two clips. Clip 2's
storyboard is generated with clip 1's last frame as its structure input, and its first panel
echoes clip 1's ending; an escalated foe inherits a visual tell from the first one. The clips
are then joined with a hard-cut ffmpeg concat. By default the cut carries an impact-frame accent
(two inverted high-contrast mono frames of clip 1's ending plus one white frame);
`spec.seam_fx: "none"` turns it off.

**Stage state.** `make_video.js` writes `state.json` after every stage. A failed stage records
its error; `--resume` re-enters there. Generation stages get at most one automatic retry, with
the same inputs. Browser stages are strictly sequential and guarded by a lock file, so a manual
run and a scheduled run can never drive the same browser tab; a stale lock left by a dead
process is reclaimed automatically.

**Provider-agnostic.** The orchestrator never talks to a service directly. Each provider is a
child script with the same contract (prompt and references in, a video file and `result.json`
out). `config/generators.json` names the active generator and its fallbacks. The browser
adapters are withheld (see `withheld/`).

**Official API path.** `make_video_atlas.py` produces the same job-dir contract through a REST
API (`atlas_cloud.py`: submit, poll, download):

- prompts come from `make_video.js --validate-only`, so both paths share one template set;
- sb1: a text-to-image call for the storyboard;
- clip1: reference-to-video with `@image1` = character sheet, `@image2` = storyboard;
- clip2: image-to-video from clip 1's last frame (the bridge, without a second storyboard);
- concat and QA as above.

The video model tier is one key in `config/generators.json`, and every tier shares the same input
surface, so a swap needs no code change.

## Local GPU path

The local path runs an open-weight video model (MiniMax H3) in ComfyUI on one 24 GB card.

**`tools/h3_local.py`** drives the ComfyUI HTTP API and absorbs three differences from the hosted
services: references are tagged `<Picture N>` instead of `@imageN`; a reference video is
truncated to the output's frame count; and a reference video is assumed to be 24 fps, so faster
sources are converted first. `--first-frame ... --loop` runs a first/last-keyframe pass with the
same image in both slots, for frame-exact loops.

**`tools/h3_queue.py`** runs a JSON list of jobs across several sessions. Finished jobs are
skipped on re-run, and SIGINT/SIGTERM let the in-flight render finish before stopping, because
killing it throws away up to 36 minutes of sampling.

**`tools/gpu_claim.sh`** is the lock every render and every vision gate runs under. The lock
alone was not enough: a vision model stays resident after its HTTP call returns, and a render
started behind it ran out of memory; in the other direction, the renderer's cache left too little
room for the vision model. So the claim takes the lock, evicts resident vision models, asks
ComfyUI to drop its cache when the next command is not a render, and waits for memory to drain.
It also keeps answers stable: a vision model loaded half on the CPU gave different answers on
the same frame.

**`tools/h3_verify.py`** scores an output against its reference on screen direction and cut
placement, matching shots by overlap because prompted cut times drift.
**`tools/h3_report.py`** scores whatever has finished and rewrites a markdown report from
everything on disk, so it is idempotent and survives a crash mid-batch.

**`tools/render_pass.py`** is the unattended loop: render each segment, grade it against the
hard gates, re-roll the seed on a real failure, and after three attempts keep the closest
candidate (ranked by hard-failure count, then motion distance from the source, then cut offset).
Nothing is dropped, so a complete video exists at the end of every run. It refuses to start
unless `tools/gate_selftest.py` passes.

**Overnight batch.** `creative_tracks/local_h3/` shows the pattern for a creative track:
`build.py` writes part-boards, prompts and a queue; `run_overnight.sh` checks the server is up
and hands the queue to `h3_queue.py`; the morning starts with `tools/stutter_check.py` on every
clip.

## Quality gates

Every gate here is local, runs at temperature 0, and was checked against footage a human had
already judged. Two rules came out of building them:

1. **A gate must have a demonstrated true positive before it is armed.** A gate that fires on
   accepted footage is worse than no gate, because an unattended loop will burn renders chasing
   failures that are not there.
2. **Check a fact on disk instead of inferring it from a sample.** Several defects lived between
   sampled frames.

| Gate | Catches | Hard or report |
|---|---|---|
| `qa_gate.py` | identity drift, unreadable action, artifacts, a flat energy arc, a bad seam | advisory in `make_video.js` |
| `tools/identity_gate.py` | G1 a third character on screen; G2 a replaced character returning | hard |
| `tools/passthrough.py` | G3 stretches where the output replays its reference video | hard (local loop) |
| `tools/h3_verify.py` | G7 cut offset against the planned shot list | hard (local loop) |
| `tools/motion_stats.py` | G8 a segment that went flat | hard (local loop) |
| `tools/board_leak.py` | G9 the storyboard image itself rendered as frames | gate (standalone) |
| `tools/stutter_check.py` | half-rate stutter and frozen frames | re-roll |

**`qa_gate.py`** scores a finished video on five axes with a 7B vision-language model:
character consistency, action readability, artifacts, energy arc and seam quality (default
thresholds 6 / 6 / 4 / 7 / 6; exit 0 pass, 2 fail). It asks the model for facts and does the
judging in code: for identity, the model lists differences between early and late frames with
evidence and the score is computed from that list, because a small model inflates direct scores.
For the seam, it answers categorical questions about a ±1 s window around the cut, including the
one that separates a good escalation from a bad one: is a large new figure in the first frame
after the cut a complete standing creature (it teleported in) or an unformed mass (it is being
born on screen)? Calibrated on six clips with known verdicts, it met five expectations and gave
identical scores across two runs, at about 21–31 s per video. It cannot see temporal artifacts
(floaty motion, frame-to-frame face flicker) in still frames, so a FAIL never blocks packaging;
it travels with the clip to human review.

**`tools/identity_gate.py`** checks, shot by shot, that the right characters are on screen and
only them. It exists because a storyboard once put the wrong character in two of seven panels,
and every other measure scored the board as fine. A third character fails a 1-v-1 segment
outright. Its known trap is documented in the code: the vision model must be called over HTTP
with the image attached, because the CLI form silently drops the image and answers from the text.
Run twice on the same clip, it returned byte-identical verdicts. Three further checks (panel-to-shot
match, style, costume) are measured and printed but do not affect the exit status, because each
fired on footage that had been accepted by eye.

**`tools/board_leak.py`** compares every frame of a clip against the exact storyboard file the
renderer was given. It was built after a leak of under half a second sat in the tail of a shot,
0.11 s past the frame the identity gate sampled. On that clip the leaked frames correlated at
0.963–0.974 with the board and every other frame at 0.148 or below, so the 0.50 threshold has
wide margins on both sides. Single-panel boards break that premise, since a correct render is
supposed to match its board; there the gate also requires the picture to stop moving (quietest
0.3 s of frame delta: 0.0008 for a spliced still, 0.093–0.653 for ten correct renders). It always
scans the un-restyled board as well.

**`tools/stutter_check.py`** finds renders where every second frame barely moves (a 12 fps
render inside a 24 fps file) by comparing even and odd frame-to-frame differences (ratio ≥ 1.6),
and frozen runs by the near-duplicate fraction. On the local model it appeared on about 45% of
renders made without a reference video and on none of 16 made with one; it varied with the seed
alone, so the response is a re-roll.

**`tools/passthrough.py`** measures how much of an output is a near-copy of its reference video.
It compares colour, not structure, at low resolution, because the storyboard panels are restyled
reference frames and an obedient output matches their shapes by design. Its threshold depends
on the target look and must be re-derived on a known-good and a known-bad run when the look
changes.

**`tools/gate_selftest.py`** runs before every loop and after any change to a gate, prompt or
threshold. It does not test that gates stay silent on accepted footage; it tests that each gate
reproduces the number in a signed-off verdict table, which catches a gate that has gone blind and
one that has started to over-fire. It has already caught one regression: adding an unrelated
question to the identity prompt hid two real defects, so each question now gets its own call.

**Pre-render checks.** `tools/shot_rules.py` fails a shot list before any render on nine rules,
each from a reviewed cut: adjacent shots must differ in at least two of subject, size, angle and
camera move; every shot names a camera move; at least 30% of shots are slow; lengths sit on the
model's frame grid; long shots carry timed internal beats; reference sheets follow the frame.
`tools/board_refs.py` derives which sheets a shot gets from what is in frame, and derives the
`<Picture N>` preamble from the list actually attached. Handing a model a character sheet asserts
that the character is in frame, so a landscape shot gets none.

## Reference analysis tools

These tools analyse footage the user owns or has licensed, to plan shots and to measure output.

- **`tools/shot_breakdown.py`** splits a clip into shots, then describes each. Timing uses
  PySceneDetect: on a reference fight clip, ffmpeg's scene filter missed four cuts in a darker
  stretch (14 shots against the correct 17). Description uses a vision model, one call per shot;
  a VLM is the wrong tool for timing and the right one for "what kind of shot is this". With
  `--motion` it adds per-shot motion energy.
- **`tools/cast_map.py`** reports who is in every shot and how many: `principal_count` (0 / 1 /
  2 / 3+, or `crowd`) routes a shot to no reference, one, or the multi-reference path. It samples
  five frames per shot instead of the midpoint, never sends near-black frames to the vision model
  (it described action in a black text card), ignores the first 0.15 s after a cut, and counts
  people as the larger of a face count and a VLM count. The face path is off by default because on
  armoured characters the detector returned only false positives; every face cluster is confirmed
  by the VLM before it counts. It writes a contact sheet so a person confirms the roster by eye.
- **`tools/motion_stats.py`** reduces a clip to mean motion and the top-to-bottom range across
  shots. Range is the number that matters: a clip whose shots all move the same amount reads as
  floaty even when the mean is right.
- **`tools/shot_prompt_lines.py`** and **`tools/h3_build_prompt.py`** turn measured screen
  direction, impact reversals, hit-stops and camera moves into per-shot prompt clauses, merged
  with hand-written shot descriptions off one shot list. Camera movement is stated explicitly
  because the local model attenuates pans about 7x when it is not.
- **`tools/build_segment_assets.py`** cuts a segment's reference clip from clean shots, merges
  shots under 0.5 s of output (the model's text encoder samples the reference at 2 fps), and tiles
  a board at a renderable ratio. **`tools/pick_char_ref.py`** picks a reference-sheet frame from
  the pipeline's own output.
- **`v2v/`** maps a character reference onto a driving video's motion (Wan 2.2 Animate, and a
  depth-conditioned whole-frame variant), after `v2v/scene_split.py` splits the driver into
  shots, since one pass cannot cross a hard cut.

## Creative tracks

One-off pieces follow a fixed route, shown by the files in `creative_tracks/examples/`:

1. **Shot list** from the brief.
2. **Reference sheets**: a character sheet and an environment frame, generated as stills and
   picked by eye. `char_sheet_parts.json` shows how a sheet prompt scopes each reference image
   ("use Image1 for face and figure only").
3. **No-storyboard video first**: the character sheet as the only image reference, and a prompt
   in the provider's structured format (image roles, subject settings, overall style, then a
   per-shot list). See `examples/action/prompt_noboard.txt`.
4. **Storyboard route only if that misses**: one fresh nine-panel board built from the approved
   references (`prompt_board.txt`, with the board as Image 1). To change a panel, regenerate that
   panel alone as a still and paste it into its cell (`cells.json` holds the cell rectangles),
   rather than editing an edited board.
5. **Review page**: every round goes on a self-contained HTML page with the media embedded, and
   the creative pick is made there.

For a single continuous take, the prompt follows the camera in one paragraph with no timed beats,
because timed beats are read as cut points.

## Known limits and next steps

Each limit below shaped a design choice above.

- **15 s per call.** Longer sequences are chained. A context-carrying chain (the previous clip
  passed as a video reference, plus the provider's last-frame output) is the next step past the
  frame bridge.
- **Seed variance.** Direction agreement swung 8–79% on identical inputs with only the seed
  changed, so no direction result counts without at least five paired seeds; cut offset is
  low-variance and is what the loop gates on.
- **Reference video carries more than motion.** In a three-arm, three-seed A/B, a reference
  video carried its medium and colour grade into the output (drawn shots: 18/21 and 17/21 with a
  reference, 2/21 without), so the local loop renders without one and gates for stutter instead.
- **Fast multi-body exchanges** are not the local model's strength; it favours one clear action
  per beat, and the shot rules and prompts are written to that.
- **Temporal artifacts** are outside what a still-frame gate sees. A second-stage video-aware
  check is the planned addition.
- **Faceless characters** fall back to a person count in `cast_map.py`; identity across shots
  then comes from the human roster check.
- **Model licences.** Check the open-weight model's licence terms before distributing its output.
